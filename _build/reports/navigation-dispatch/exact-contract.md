      const res = await page.goto(path);                                              // 265

**Line 265 is the test's first statement.** There is no `beforeEach` in this
describe block and no fixture setup of its own, so nothing in the test's own
scope precedes the call under investigation.

## The call

| | |
|---|---|
| Call | `page.goto(path)` |
| Argument 1 | `'/nagyvallalat.html'` — a relative path, resolved against `baseURL` |
| Argument 2 | **absent** |
| `waitUntil` | `'load'` — Playwright's default, not set here |
| `timeout` | **not set on the call.** With no `navigationTimeout` configured, the navigation is bounded only by the test budget |
| Effective budget | **30 000 ms**, the project `timeout` |
| Resolved target | `http://127.0.0.1:4322/nagyvallalat.html` |

`navigationTimeout` and `actionTimeout` are set nowhere in `playwright.config.ts`,
so both are `0` (unbounded) and the test budget is the only ceiling. This is why
the failure surfaces as `Test timeout of 30000ms exceeded` and not as a navigation
error — a distinction the G6 bundle already records and which matters to §37.

### Is `about:blank` the expected initial state for this contract?

**Yes, always.** Playwright Test builds a fresh `BrowserContext` and a fresh
`Page` for every test, and a fresh page's URL is `about:blank` until something
navigates it. This contract's first statement is its `goto`, so the page cannot
be anywhere else. The G6 bundle's `contextPages: 1` and `navigationsInThisTest: 0`
confirm it was the ordinary case and not a leaked page from an earlier test.

So `about:blank` is **not an anomaly** and must not be read as one. What it does
establish is narrower and still useful: the stalled navigation was this page's
**first**, which is the condition §22 exists to control for.

## One fact from the bundle that constrains everything after it

In fixture teardown, **after** the 30-second stall, on the same page:

* `page.evaluate(...)` returned `{ readyState: "complete", href: "about:blank", … }`
* `page.title()` returned
* `page.screenshot()` wrote a 45 KB PNG
* `crashed: false`, `closed: false`

The browser process was alive, the page target was alive, and the protocol
connection was carrying commands and answering them — *while* the navigation
begun 30 seconds earlier had still produced nothing. Whatever stalled did not
stall the connection, the process, or the page.

That is the constraint the rest of this investigation is built on, and it is
sharper than it first looks on WebKit specifically. See `instrumentation.md`.
