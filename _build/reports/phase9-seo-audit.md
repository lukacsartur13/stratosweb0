### Duplicate content

The two duplication risks that existed have both been closed in this phase:

1. **The homepage had two addresses.** `/` and `/index.html` both answered 200
   with the same document, the shells' canonical said `/`, and the sitemap and
   every internal link said `/index.html`. Fixed at the generator, and
   `/index.html` now 301s. See `phase9-redirect-map.md`.
2. **The Impact Program description was never translated.** All three locales
   shipped the Hungarian sentence, so the EN and DE pages carried a description
   in the wrong language *and* were byte-identical to a third page. Found by
   this audit's duplicate check rather than by reading, which is the point of
   having the check. Translated; the three are now distinct and each is in its
   own language.

## 3. The three homepages

They are a React application. Their `<h1>`, and all their body content, is
produced by the bundle and is not in the shell this script reads. So this audit
deliberately does not answer "does the homepage have one `<h1>`" — it records
the deferral by name instead:

> `has one h1 and a skip link` — `tests/public-site.spec.ts`, which drives a real
> browser and asserts exactly that, in all three locales.

Reporting a pass here would have meant reading the wrong artefact; reporting a
failure would have meant reporting a defect that does not exist. Everything the
shell *does* own — title, description, canonical, hreflang, Open Graph,
structured data, `lang` — is audited normally and passes.

**Known characteristic, not a defect:** a crawler that does not execute
JavaScript sees the homepage's `<head>` and its chrome, and no body copy.
Google renders JavaScript and will see the whole page; other crawlers vary. This
is inherent to the homepage's design and is out of Phase 9's scope to change.

All nine are the three case studies in three locales, marked `summary` in

equity. None has a sitemap entry, and none received case-study structured data.

**No draft case study is promoted anywhere.** Asserted three ways: no sitemap
entry, `noindex` in the document, and no `Article`/`CreativeWork` node in the
structured data.

### No hidden SEO-only headings

No `<h1>` is visually hidden, none is off-screen positioned, and there is no
keyword block anywhere in the markup. The `<h1>` on every generated route is the
page's visible headline.

## 5. The 43 warnings, and why none is a failure

| Rule | Count | Assessment |
|---|---|---|
| `hreflang-noindex` | 27 | The nine `noindex` case studies, each referenced by three alternates. This is **correct and intended**: the pages exist in three languages and are cross-linked; they are simply not offered for ranking. Removing them from each other's hreflang set would be wrong. |
| `title-length` | 11 | Titles over 65 characters, which is where Google usually truncates. All eleven read correctly when truncated — the brand suffix is what is lost. A judgement about each page, not a rule. Listed per route in the JSON. |
| `description-length` | 5 | 166–176 characters against a 165 guideline. All five are German or Hungarian, where the same sentence is simply longer. Shortening them to hit a number would cost meaning to gain nothing measurable. |

None of the three is a correctness problem, and each is left to a human because
the right answer is a decision about the page rather than about the site.

## 6. What could not be validated here, and why

| Item | Blocked on |
|---|---|
| Live HTTP status of every route | The domain has not moved. `npm run audit:seo` reads files; `scripts/route-audit.mjs` drives a browser against a local server. Neither is the production edge. |
| The final origin in every canonical | The origin is **resolved**, never written down — `SITE_URL`, then Netlify's `URL`, then `https://stratosweb.hu`. Every canonical, `og:url`, hreflang and sitemap entry is built from it, and the audit asserts they all agree with each other and with `site-origin.mjs`. What it cannot assert is that the resolved value is the one the site will finally be served from. |
| Netlify "Pretty URLs" | A dashboard setting that, if on, 301s `/page.html` to `/page` — which would make every canonical this build emits point at a redirect. **REQUIRES USER FACTUAL INPUT**; see `phase9-redirect-map.md` §3. |
| Indexing behaviour, coverage, rendering as Google sees it | Search Console on the final domain. See `phase9-search-platform-setup.md`. |

**Post-cutover verification list** (four commands, in order):

```
curl -sI https://stratosweb.hu/kkv.html            # 200, not 301
curl -sI https://stratosweb.hu/index.html          # 301 -> /
curl -sI https://stratosweb.hu/no-such-page        # 404
curl -s  https://stratosweb.hu/robots.txt          # must NOT be Disallow: /
```

The last one is the one to watch. `robots.txt` is `Disallow: /` on any
`netlify.app` origin, deliberately, and it stops being so the moment the custom
domain becomes the primary address in Netlify. If the domain is attached but not
marked primary, the site stays uncrawlable and nothing about the page would say
so.
